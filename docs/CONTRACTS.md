## Bridge API (`window.yaseenDocs`, locked in GRO-2153 — Desktop A1)

The desktop app has no HTTP server (GRO-2095 D2): the renderer is sandboxed and calls the typed bridge the preload installs; `ipcMain.handle` answers from the main process (GRO-2157 deleted the server and every HTTP path). All paths are absolute POSIX paths; no jail — any absolute path is allowed. Every method rejects with a plain `BridgeError { code, message, path?, mtime? }` (`BridgeErrorCode` in `shared/types.ts`, plus `CONFLICT` which carries the disk mtime); the client's `api.ts` wraps it in `BridgeRequestError` (same fields) so the renderer can `instanceof` it.

| Bridge | Notes |
|---|---|
| `tree(root)` | `TreeResponse` — recursive; only vault files: `.md`/`.markdown` (`kind: 'markdown'`) and `.base` (`kind: 'base'`, GRO-2123); every dir shows, vault files or not (GRO-2022); dot-entries and `node_modules` skipped; dirs before files, each sorted case-insensitive. Missing / not a dir → `NOT_FOUND` / `NOT_A_DIRECTORY` |
| `readFile(path)` | `FileResponse` — raw UTF-8 content incl. frontmatter; `.md`/`.markdown`/`.base` only (else `UNSUPPORTED_EXTENSION`); `TOO_LARGE` above 10 MiB |
| `writeFile({ path, content, expectedMtime? })` | `FileWriteResponse { path, mtime, size }` — vault files only; atomic write (`<name>.tmp-<rand>` + `rename`); parent dir must exist; if `expectedMtime` is given and the disk mtime differs → rejects `CONFLICT` with the disk `mtime` and nothing is written |
| `createDir(path)` / `createFile(path \| { path, content? })` | `CreateDirResponse { path }` / `CreateFileResponse { path, mtime, size }` — parent must exist (else `NOT_FOUND`); `.md`/`.markdown` created empty, `.base` seeded with exactly `views:\n  - type: table\n    name: Table\n` (else `UNSUPPORTED_EXTENSION`); the object form's `content` (Bible B, GRO-2202) replaces those defaults and lands in the same write — content-at-create for scaffolded pages and starter bases, no create-then-write race; `wx` write, never overwrites: exists → `ALREADY_EXISTS` |
| `pickFolder()` | `PickFolderResponse` — Electron `dialog.showOpenDialog` (`openDirectory` + `createDirectory`) parented to the calling window (`desktop/src/main/ipc/dialog.ts`). Picked → `{ path }` (no trailing `/`); dismissed → `{ cancelled: true }`; dialog failure → `PICKER_FAILED` |
| `watch(root, listener) → unsubscribe` | `WatchEvent`s: first `ready` (at once for late joiners of an already-watched root), then `add` / `change` / `unlink` (+ `mtime`) for vault files and `addDir` / `unlinkDir`; a bad root yields one `error` event and no subscription. One chokidar per root in main shared by every window (`ignoreInitial: true`, `awaitWriteFinish: { stabilityThreshold: 200 }`, ignores dot-entries and `node_modules`); a window going away drops its subscriptions |
| `index(root)` | `IndexResponse { root, records, generatedAt, types? }` (GRO-2129; `types` = the `.obsidian/types.json` assignments, read per call, for cell editor inference — 5B, GRO-2142) — every markdown note under `root` as an `IndexRecord` (path/stat fields, frontmatter `properties`, `aliases` (E2, GRO-2214), `tags`/`links`/`embeds` incl. body scan — D7), sorted by path; `.base` files are never records. Full scan on first call per root (`desktop/src/main/vaultIndex/`), watcher-incremental after, evicted after ~10 min idle. Client: `useIndex(root, watch)` fetches once per root and refetches (300 ms debounce) on markdown `add`/`change`/`unlink`, `unlinkDir` and `ready` events |
| `coldDiff(root)` | `ColdStartDiffResponse { root, scannedAt, cacheStatus, added, removed, changed } \| null` (Links E1c, GRO-2242) — the cold-start reconcile diff the persistent index cache computed for `root` (see "Property index"): `added` = on disk but not in the cache (ON-DISK stats), `removed` = in the cache but gone from disk (CACHED stats), `changed` = stat drifted (re-scanned). Null before the first `index(root)` build for the root and again after idle eviction — the E1c detector reads it AFTER the first index snapshot. Honest miss semantics: trust the three lists only when `cacheStatus === 'hit'` — on `miss`/`corrupt`/`version-mismatch` they are empty and the status says why |
| `readAsset(root, ref)` | `AssetResponse { path, mime, data, size }` (GRO-2139 amended by D10: a bridge method, never a route) — a local image under `root` as base64 + mime (from the extension) for a `data:` URL. `ref` is a wikilink target or path (`\|alias` / `#heading` stripped like the index's link extraction): with a `/` it is tried root-relative first; else/fallback Obsidian's shortest-path rule — case-insensitive basename match anywhere under root, first hit in a breadth-first walk (a shallower match always wins) with each directory's entries sorted case-insensitively, dot-entries and `node_modules` skipped. Images only: png/jpg/jpeg/gif/webp/svg/avif/bmp (`IMAGE_EXTENSIONS`, else `UNSUPPORTED_EXTENSION`); no match → `NOT_FOUND`; above 10 MiB → `TOO_LARGE` (`desktop/src/main/fs/assets.ts`) |
| `state.get/setSettings/setSidebarCollapsed/pushRecent/removeRecent/setFolder/setFolds/setBaseGroups/onChange` | `AppState` in the main-owned `yaseendocs.json` (GRO-2159, D9; replaces the retired renderer web-storage `mdapp.*` keys); targeted mutators so windows never clobber each other; `removeRecent` drops a dead folder from the MRU (C2, GRO-2164); `setBaseGroups` replaces one base view's collapsed group keys (4C, GRO-2137) |
| `window.identity/setIdentity/open/duplicate/onFlush` | window identity from `?win=<id>` (GRO-2159, see "App state"); `open({ root, file })` = an independent new window (GRO-2160 — the sidebar context menu's "Open in new window", D2 GRO-2168; ⌘-click opens a background tab instead since I3, GRO-2235); `duplicate()` = same folder + file + tabs as the calling window, cascaded bounds (the ⌘⇧N gesture, GRO-2167); `onFlush(listener)` = the close/quit flush handshake — main holds the close until every listener settled, hard 5 s cap (GRO-2160, see "Multi-window") |
| `menu.onOpenFolder/onOpenRoot` | pushes from the application menu to the focused window's renderer (B3, GRO-2161): File › Open Folder… (⌘⇧O) → run the pick-folder flow; File › Open Recent chose `path` → switch the root in place (see "Menus & shortcuts") |
| `link.onOpenFile/onNotice` | pushes from deep-link routing (E1, GRO-2171): `onOpenFile(path)` = a link resolved to this window (the path is guaranteed inside its root); `onNotice(message)` = a link could not be opened — show it unobtrusively, never a dialog (see "Links") |
| `file.rename({ oldPath, newPath })` / `file.onRenamed` | in-app rename/move (Links E1 GRO-2194, E1b GRO-2241 — see "Links": Rename). Files rename in place or move BETWEEN folders; the extension KIND stays unchanged — md↔md (`.md` ↔ `.markdown` is one kind), base↔base (`BAD_REQUEST`; wrong/missing extension → `UNSUPPORTED_EXTENSION`). Directories rename/move too (`kind: 'dir'` in the response; no extension rules): dot-dirs are refused as source or target (`BAD_REQUEST` — invisible infrastructure), a folder cannot move inside itself, and the CALLING window's own vault root is refused (`BAD_REQUEST` — root identity is a recents/vault question, out of E1b scope; another window's subfolder-root is fine and gets repaired). The target's parent must already exist (`NOT_FOUND`, attributed to the parent — never a mkdir). Never overwrites: the target is pre-checked → `ALREADY_EXISTS` (fs.rename has no `wx`; pre-check + the single-instance lock is the accepted race posture; a case-only rename statting its own inode at the target is allowed). The SAME handler then repairs the app state — every stored path AT or UNDER the renamed entry follows: window `root`/`file`/`tabs` (via `normalizeTabs`; a window ROOTED at the renamed folder follows too), recents, each folder-state key and its `expanded`/`lastFile`/fold keys/baseGroups keys (`store.renamePath`, one commit) — and pushes `file:renamed { oldPath, newPath, kind }` to EVERY window (`onRenamed`), whose renderer remaps its open tab(s) in place (`useTabs` `rename`, or the `rename-dir` prefix remap). The vault index is NOT pushed: the shared watcher's unlink+add echo heals it (no double-processing) |
| `file.repairRename({ oldPath, newPath })` | Store/tab repair for a rename that ALREADY happened on disk (Links E1c, GRO-2242 — the confirmed-banner path, see "Links": Rename → External renames). There is no fs work: the handler validates the claim — `newPath` must EXIST (its stat derives `kind`), `oldPath` must NOT (`BAD_REQUEST` — a live old path means the hypothesis was wrong; refuse, never guess), extension-kind and dot-dir rules mirror `rename` — then runs the SAME `store.renamePath` repair and pushes the SAME `file:renamed { oldPath, newPath, kind }` to every window, so tabs, editor continuity and title/hash reuse the E1 downstream unchanged. No vault-root guard (nothing moves; a window rooted at an externally renamed folder is exactly what the repair heals) |
| `file.delete({ path })` / `file.onDeleted` | In-app delete to the **system Trash** (GRO-2272 — see "Delete"). `shell.trashItem` and nothing else: there is no `fs.rm` anywhere on this path and **no permanent-delete fallback** — a trash failure rejects `IO_ERROR` and the entry stays on disk (a filesystem with no Trash is exactly where destroying it would be worst; `remove.test.ts` asserts the file survives). Refuses (`BAD_REQUEST`) dot-entries — invisible infrastructure the tree, index and watcher never show — and the CALLING window's own vault root (root identity is a recents/vault-management question, the same split as `rename`); ANOTHER window rooted inside a deleted folder is allowed and falls through to that window's existing `onRootMissing` repair. Missing path → `NOT_FOUND`. No extension gate: every folder in the tree is deletable regardless of contents. The SAME handler then drops every stored reference (`store.removePath`, one commit: window `file` — promoted to an heir tab by `useTabs`' own right-then-left ladder rather than nulled, so surviving tabs are not discarded — plus tabs through `normalizeTabs`, recents, folder-state keys and their `expanded`/`lastFile`/fold keys/`baseGroups` keys; window `root` is deliberately left alone) and pushes `file:deleted { path, kind }` to EVERY window (`onDeleted`), whose renderer retires the editor's autosave and THEN closes the tab — that order is what stops a dirty buffer resurrecting the file. The vault index needs no push: the watcher's `unlink` / `unlinkDir` echo heals it (`trashItem` is a MOVE at the fs layer, verified against the app's own chokidar options). Notes referencing a deleted page are left **byte-identical** — their `[[links]]` simply go unresolved (LOCKED decision C) |
| `shell.reveal({ path })` | Reveal in Finder (GRO-2274 — **VS Code parity is the locked reference for this issue**). `shell.showItemInFolder`: the entry is selected **in its parent**, for files, folders and the vault root alike — deliberately NOT `shell.openPath`, which would open a folder's contents; the verb is "Reveal", and VS Code and Obsidian both behave this way. The path is stat'd first so a stale row (deleted or moved externally) rejects `NOT_FOUND` — `showItemInFolder` returns `void` and silently does nothing for a missing path, which reads to the user as a broken menu item. Read-only, so unlike `file.delete` / `file.rename` there is deliberately **no dot-entry guard and no extension guard**: any absolute path the app can already show is fair game, matching the "no jail" posture above. No store repair and no broadcast — nothing changes — but still enveloped so the `NOT_FOUND` reaches the renderer as a passive notice |
| `vaultConfig.read/write/onChange` | Vault-local config in `<root>/.yaseendocs/` (Desktop J, GRO-2188) — the `.obsidian/` analogue: travels with the vault. `read(root, name)` → parsed JSON or `null` (missing folder/file, or malformed JSON — one `console.warn`, never a throw); reading NEVER creates the folder. `write(root, name, value)` `mkdir -p`s the dotfolder lazily and writes pretty-printed JSON atomically (tmp + rename); `name` must be a plain `<stem>.json` basename (separators / `..` → `BAD_REQUEST`, other extensions → `UNSUPPORTED_EXTENSION`). The shared vault watcher never sees dot-entries, so main runs one tiny chokidar per open-vault root scoped to the dotfolder (`desktop/src/main/vaultConfig.ts`, subscribed per `AppState.windows` root, dropped with the last window); own writes notify synchronously and their watcher echo is deduped by mtime, external edits (sync tools) are debounced — either way every window gets `vaultConfig:changed { root, name }` and filters by its own root. `.yaseendocs` never appears in the tree/sidebar, the vault index, or base results |

One user-global JSON file owned by the main process: `app.getPath('userData')/yaseendocs.json` = `~/Library/Application Support/Yaseen Docs/yaseendocs.json` (`app.setName('Yaseen Docs')` runs before anything reads userData; `--user-data-dir=<dir>` relocates it, which is how the Playwright checks seed state). Renderer web storage is not used at all. The renderer never touches the file: it reads a cache (`storage.ts` in client lib, filled by `storage.init()` before the first render) and writes through the targeted `state.*` mutators; `desktop/src/main/store.ts` owns the file. Nothing here is ever written into the vault or the markdown.

Write semantics: every mutation updates memory, notifies `onChange` listeners synchronously and schedules one debounced (150 ms) atomic write (`<file>.tmp-<rand>` + rename, pretty-printed JSON, parent dir created on demand); `flush()` writes at once and `before-quit` holds the quit until it lands (`event.preventDefault()` + `app.exit(0)`), so nothing is lost on ⌘Q. A file that is unparsable, not an object or not `version: 1` is moved to `yaseendocs.json.corrupt-<epoch>` and the defaults are used — the bad file is never overwritten silently. Unknown top-level keys are dropped on load.

Live broadcast: after any change — from any window, or from main itself (window upserts) — every live `BrowserWindow` gets `state:changed` with the whole new state; the preload surfaces it as `state.onChange`, the client cache replaces itself and `storage.subscribe` listeners fire (`App` re-reads settings and `sidebarCollapsed`). A window's own writes update its cache optimistically and do not fire its subscribers until the echo arrives.

Per-window identity: main loads each window as `<renderer>?win=<id>` and keeps a `webContents.id → window id` registry (`desktop/src/main/windows.ts`). `window.identity()` answers `{ id, root, file }` from `windows[]` for the calling window (`BAD_REQUEST` for an unregistered sender, `NOT_FOUND` once the entry is gone); `window.setIdentity({ root?, file? })` merges into that entry (absolute paths or null; `id` and `bounds` cannot be changed this way). On the client, `storage.getRoot()` IS the identity's root; `setRoot` also clears `file` when the root changes; `setLastFile(root, file)` records both the folder's `lastFile` (for the next time that folder opens) and the window's `file` (what is open now).

## Multi-window (D3/D6 — GRO-2160/2167/2168/2169)

The window manager (`desktop/src/main/windows.ts`) is Electron-free — `main/index.ts` injects window construction and display geometry as a `WindowHost`, so everything below runs under vitest with fakes.

- **Restore** (D3): on launch, one window per `AppState.windows` entry; an empty state seeds a single Welcome window (`root: null`). Restored bounds are clamped fully inside the display work area they overlap most (fully off-screen → the nearest one; oversized → shrunk to fit) — so a window from an unplugged display always lands somewhere visible. Bounds changes (`move`/`resize`) are committed to the state debounced (250 ms per burst — one `state:changed` per drag).
- **Duplicate** (GRO-2167): `⌘⇧N` / `window.duplicate()` — same folder, same file, same TABS (the copy carries the whole set), fresh id, bounds cascaded +24 px and clamped at the display edge. A Welcome window duplicates to another Welcome window.
- **Open beside** (D2, GRO-2168): a file row's context-menu "Open in new window" → `window.open({ root, file })` — an independent window on the same folder with that file open. Open Recent's ⌥-click and deep-link routing use the same `openWindow` path (default bounds, clamped). ⌘-click on a sidebar file row is NOT this gesture any more: since I3 (GRO-2235, locked) it opens a background tab in the SAME window — see Tabs below.
- **Tabs** (GRO-2232/2234/2235): a window's open files are `WindowEntry.tabs` (absolute paths, left→right) with `file` doubling as the ACTIVE tab. Invariants, repaired by `normalizeTabs` on load and held at the IPC boundary on every `setIdentity`: `file ∈ tabs` whenever non-null (a legacy entry without `tabs` becomes `[file]`), `tabs: []` ⇔ `file: null`, and `tabs` de-duplicated by path — ONE editor per path per window, so opening an already-open file (sidebar click, deep link, ⌘-click) activates its tab and never duplicates it. After boot the RENDERER owns the model (`client/src/tabs/useTabs.ts`) and mirrors every change down as ONE explicit `setIdentity({ tabs, file })` — never a `{ file }`-only patch. That identity write always goes out; the accompanying `folders[root].lastFile` write does NOT when the active file did not change (GRO-2197), because a background-tab open, a drag-reorder or a non-active close would otherwise commit a no-op folder patch whose `state:changed` broadcast re-renders every window and every mounted editor. Note for readers of the code: the `// rule N` citations in `useTabs.ts` / `App.tsx` number the LOCKED tab rulings of GRO-2232/2234/2235, which this bullet summarises in prose — they are not indices into the numbered Editor list further down this file. Gestures: a sidebar click or routed deep link opens in the CURRENT tab (a link never spawns a tab or window when its file's tab exists — it activates it); ⌘-click a sidebar file row appends a BACKGROUND tab at the end of the strip without activating it; tabs drag-to-reorder; middle-click or ✕ closes. The ⌘W ladder: close the active tab (its right neighbour takes over, else the left) → closing the last tab leaves the empty state with the window ALIVE → ⌘W with zero tabs closes the WINDOW through the real close path. Restore/relaunch reopens every tab with the stored active one on top; only VISITED tabs mount editors (a background tab's editor lazy-mounts on first activation). Activating a tab whose file vanished on disk closes it through the sidebar's `onFileMissing` path (confirmed against a fresh tree); background tabs are never probed.
- **Single instance** (GRO-2160): `requestSingleInstanceLock` — a second launch quits itself; the first instance gets `second-instance`, routes any `yaseendocs://` URLs in its argv (E1), else focuses a window.
- **Close/quit flush handshake** (GRO-2160): `close` is ALWAYS intercepted — main commits the bounds, sends `app:flush`, the renderer flushes its autosaves (`window.onFlush` listeners) and acks `app:flushed`, then main `destroy()`s the window; a hung save can never block close (hard 5 s cap). A user close removes the window's state entry; the LAST window closing quits (`window-all-closed`), and quits — like ⌘Q's sequential flush of every window — keep the entries so relaunch restores them.
- **Same file in N windows** (GRO-2169 — D6/D9/A4): no dedicated sync channel — the disk-change path IS the sync. A window's save lands on disk → the shared watcher emits `change` to every window → each other window reloads silently when clean, or shows the conflict bar (Reload / Keep mine) when dirty. Echo suppression is per window: each window's own `Autosave` controller holds the mtime from ITS last `writeFile` response and only drops events matching that mtime (client `editor/Editor.tsx` / `bases/BaseHost.tsx`), so window A's save is never mistaken for window B's echo. Folds are shared per file through the app state (`folders[root].folds`) — last writer wins, applied the next time the file is opened; live windows are NOT re-folded. Zoom is per window and in-memory only, never persisted. One chokidar per folder in main, shared by every window and subscription (`desktop/src/main/fs/watchers.ts`); it closes when the last subscriber leaves.

## Links (E1/E2/E3 — GRO-2171/2172/2173)

- **Format** (E1, locked D7): a note's shareable URL is its `yaseendocs://` file link — path-only, absolute, percent-encoded (`yaseendocs:///Users/me/vault/My%20note.md`), no vault id; an optional `?root=` (also a percent-encoded absolute path) overrides which folder it opens under. `shared/links.ts` (`fileLink`/`parseFileLink`) is the ONE encoding, shared by main's parser and the client's generator; `encodeURI` plus `#` and `?` encoded on top, so either never truncates the path.
- **Copy link** (E3): the sidebar context menu's "Copy link" on a FILE row puts exactly `fileLink(path)` on the clipboard (folders and blank space get no item).
- **Routing** (E1): a link — clicked anywhere (`open-url`), handed over by Finder's Open With (`open-file`, E2 — the plain path is re-encoded through `fileLink` and rides the same pipeline), or in a second launch's argv — routes identically (`resolveLinkTarget`): (1) the open window whose root contains the file — most specific root wins, Welcome windows never match — is focused and switches to it (`link.onOpenFile`); (2) else a new window opens on the most recent recents folder containing it (`?root=` pins the effective root instead when it contains the path); (3) else on the file's parent directory. Links queue until the windows are restored on cold start (`linkQueue.ts` — macOS fires `open-url` before `ready`), so hot and cold behave the same.
- **Failure surface** (E1): a non-markdown or missing target — or an unparsable link — focuses a live window and shows the passive in-window notice (`link.onNotice`), never a dialog.
- **In-window wiki-link navigation** (Links C, GRO-2192) is RENDERER-LOCAL: clicking a `[[wikilink]]` in the editor drives this window's own tabs API (`openCurrent` / `openBackground`, Editor rule 23) — no IPC, no main-process involvement; the manager's `routeToFile` (the Routing bullet above, `windows.ts`) stays the ONLY path that focuses another window or creates one.
- **Aliases** (Links E2, GRO-2214): a note's frontmatter `aliases` are extra NAMES it answers to across the whole app — the index carries them (`IndexRecord.aliases`, table below), the ONE resolver consults them LAST (see "Link resolution"), so `[[CAC]]` renders resolved (Editor rule 23) and clicking it opens the aliased page, and the `[[` picker offers the page under each alias, inserting the piped `[[Name|Alias]]` (rule 24). Two consequences pinned elsewhere: alias values are never outgoing `links`, and a rename never rewrites an alias-form link (Rename, below).
- **Rename** (E1, GRO-2194 — decision E of GRO-2096, LOCKED): an in-app rename updates links AUTOMATICALLY, no prompt (Obsidian's default). Scope since E1b (GRO-2241): FILE rename and cross-directory move, and FOLDER rename — the extension kind stays unchanged for files; E1b lifted E1's same-parent and files-only guards. Gestures: the sidebar file- OR folder-row context menu's "Rename" → inline input over the row (files: prefilled name minus extension, `validateEntryName` + the `entryPath` extension re-append via `renamedPath`; folders: raw name, no extension logic; same name = no-op; no hotkey v1); and drag a FILE row onto a folder row or the root header → move there (same pipeline; no multi-select, no folder dragging — Future). Flow, in order: (1) the originating window FLUSHES its own autosave for the file, so the buffer travels with it; (2) it snapshots the vault index BEFORE renaming (afterwards the old name no longer resolves); (3) `file.rename` renames on disk, repairs the app state and broadcasts `file:renamed` (bridge table above); (4) every window's renderer — BEFORE remapping its tab — captures a DIRTY old-path buffer, RETIRES the old autosave controller (its unmount/close flushes become no-ops: the old path can never be resurrected) and stashes the buffer under the new path, where the freshly mounted editor applies it as an UNSAVED change (`lib/renameContinuity.ts`; title/hash follow the active tab's existing effects); (5) the originating window rewrites every referencing note (`links/renameLinks.ts`): the referencing set is the index records whose `links`/`embeds` resolve — through THE shared resolver (`resolverFor`) — to the old path; per file read → rewrite → write with `expectedMtime`, one CONFLICT re-read-retry, a second conflict skips the file. Rewrites preserve `|alias` and `#heading`/`#^block`, preserve link FORM (bare→new bare name, pathed→new root-relative, explicit extension stays), cover `![[embeds]]`, skip fenced/inline code (a length-preserving mirror of the index's `stripCode`), and touch frontmatter only as whole-value exact `[[…]]` strings via `setFrontmatterProperty`. Outcomes are PASSIVE (never a dialog): one summary notice "Updated links in N notes" (+ "; M skipped (unsaved changes)"), `ALREADY_EXISTS` and other failures land in the same link-notice; another window's dirty referencing editor falls back to the normal conflict bar — EXCEPT for a referencing note that the rename itself remaps (a folder rename moving an open dirty note), whose editor remounts, re-reads from disk and adopts the post-rewrite baseline, so the conflict never surfaces (GRO-2197 audit, deferred). Accepted residual race: a save already in flight over IPC when the rename lands can still recreate the old path — the systematic paths (debounce, unmount flush, close flush) are all covered by the retire step. ALIAS-form links are never rewritten (E2, GRO-2214): `[[CAC]]` reaching the moved file through its frontmatter `aliases` keeps resolving afterwards — the alias travels with the file — so the referencing-set probe resolves BY NAME ONLY (`resolverFor(records, root, { aliases: false })`); a note referencing the moved file only by alias is never even read. KNOWN GAP (GRO-2197 audit, deferred): the banner's N and the number of notes actually written can still disagree on a pure MOVE — N counts every note whose links RESOLVE to the old path, while the rewrite writes nothing for a bare link that stays bare, and in a pure move every bare link stays bare, so "update N links?" can be followed by "Updated links in 0 notes". Closing it needs N to become link-FORM aware, not just resolution aware. E1b bare-vs-pathed rules, LOCKED: a FOLDER rename rewrites only PATHED links/embeds (to the new root-relative path) — bare-name links keep resolving (names unchanged) and stay BYTE-IDENTICAL; a FILE move keeps a bare link bare only when the bare form still resolves to the moved file AFTERWARDS (checked through the resolver against a POST-move record set — the shallowest rule can hand the name to a duplicate), else it escalates to the pathed form (a kept bare form is never spliced, padding included). `.base` embed targets resolve over a PRE-rename tree snapshot through `resolveBasePath` (the documented root-relative-then-BFS rule; `.base` files are never index records): pathed base embeds rewrite like links, a bare `![[X.base]]` stays bare only while the (new) name is UNIQUE in the tree, and with no tree snapshot base embeds are left alone (conservative). Refusals (all passive notices): existing target → `ALREADY_EXISTS`; missing target parent → `NOT_FOUND` (never a mkdir); dot-dirs and the calling window's own vault ROOT → `BAD_REQUEST` (root identity is a recents/vault question, out of E1b scope). A window rooted AT (or under) the renamed folder follows it live: its tabs prefix-remap and its local root state remaps without an identity write (main's store repair already moved `WindowEntry.root`).
- **External renames** (E1c, GRO-2242 — LOCKED ruling): a rename/move done OUTSIDE the app (Finder, terminal, sync tools) is detected and repaired too — CONFIRM-FIRST, never automatically, never a dialog (ahead of Obsidian, which does not repair external renames at all — verified). ONE hypothesis detector (`client/src/links/renameDetector.ts` `detectRenames`), TWO feeds: (a) COLD-START — after the first index snapshot the client reads `coldDiff(root)` (bridge table above) and joins `removed` × `added`; trusted only on `cacheStatus === 'hit'`; (b) WHILE-RUNNING — consecutive `useIndex` snapshots (`WikilinkIndexBridge.onSnapshot` — no new watchers, no polling), diffed into the same removed/added shape, with UNMATCHED removals and additions carried forward exactly ONE snapshot generation. That carry is load-bearing, not belt-and-braces (GRO-2197): chokidar's `awaitWriteFinish` holds an `add` back ~200 ms while `unlink` fires at once, and the index applies `unlink` synchronously but `add` behind an async `scanFile`, so the index genuinely passes through a ~100 ms window showing the removal WITHOUT the addition. The 300 ms refetch debounce usually straddles both — but when it does not, the pair splits across two generations, `detectRenames` never sees it, and the hypothesis was previously lost forever (measured: `externalRename.spec.ts` steps 1 and 3 failed ~50-100% of runs under CPU load, 0/9 idle). Carried entries are re-validated against the new snapshot first (a removal whose path came back was a save, not a rename; an addition that vanished again is dropped) and only the CURRENT generation's leftovers are carried on, so the memory is bounded to one generation. Guard rails, firm: markdown files only; join key = EXACT (size, mtime) equality (macOS rename/move preserves both); zero-byte files skip; only UNAMBIGUOUS 1:1 pairs — a signature carried by several removed or several added files skips entirely (no guessing); equal basenames (a pure move) still hypothesize — pathed links may need rewriting. Either feed lands in ONE passive app-level banner (`useExternalRenames` — the link-notice idiom with two actions, one hypothesis at a time, oldest first): "Looks like `X` became `Y` — update N links?" [Update] [Dismiss]. N is the rewrite engine's own referencing-set count (`countLinkReferences`, the dry-run twin of `updateLinksAfterRename`, over a PRE-rename snapshot synthesised by re-pathing the moved record back — `preRenameRecords`); N === 0 → no banner, nothing happens at all. Update → (1) `file.repairRename` (bridge table above — store/tabs/editors follow via the existing `file:renamed` downstream; a refused claim, e.g. the old path came back, lands as a passive notice), (2) the E1/E1b rewrite engine old→new over fresh index/tree snapshots re-pathed pre-rename, (3) the usual summary notice — always shown here (the user explicitly asked). Dismiss → the pair joins a SESSION-level dismissed set and is never re-offered (the next refetch re-detects the same diff; the set is what keeps it quiet); a handled (Updated) pair joins the same set. In-app renames echo through the watcher as identical unlink+add pairs, so every `file:renamed` push also feeds the suppression set (exact pair for files; prefix mapping for dirs, since a folder rename echoes as one pair per moved note) — own renames never banner. The DIR prefix mappings are cleared on a root switch (GRO-2197): they exist only to swallow the current vault's echoes, and left standing they sat in the per-hypothesis linear scan for the rest of the session, across vaults. (The dismissed PAIR set is session-level by ruling and deliberately survives a root switch — its keys are absolute paths.)
- **Backlinks** (Links D, GRO-2193 — decision D of GRO-2096, LOCKED): the reverse direction is RENDERER-LOCAL too. "Linked mentions (N)" is a collapsible block at the bottom of the note's own scroll, computed per render from the index snapshot the window already has through the ONE resolver (so alias-form links count) — no reverse map in main, no new IPC, no index field, no new watcher. Context snippets are read on demand for the rows actually shown. Full rules: Editor rule 25.
- The in-app `#/abs/path.md` hash (Editor rule 17) is separate and unchanged.

## Editor rules (client)

1. **Frontmatter**: on load, `splitFrontmatter(content)` → `{ frontmatter, body }`; only `body` goes into Crepe. On save, write `frontmatter + getMarkdownForSave(crepe)`. Frontmatter is re-prepended byte-identically (Crepe would otherwise turn `---` YAML into `***` + paragraph + setext heading underline).
2. **Crepe construction**: always via `createCrepe()` — features come ONLY from `src/editor/featureConfig.ts` (`ENABLED_FEATURES` / `DISABLED_FEATURES`, every `CrepeFeature` classified; ImageBlock, TopBar, AI off; `featureConfig.test.ts` asserts the running editor loads exactly the allowlist), list_item content `block+` (extended from GFM task item schema), `markdownUpdated` listener wired.
3. **Save post-processing**: `postProcessMarkdown()` un-escapes `\[\[` → `[[` (wikilinks/embeds).
4. **Replacing content in a live instance** (external change / Reload): `setMarkdown(crepe, md)` → `replaceAll(md, true)` from `@milkdown/kit/utils`, keeping focus and caret. TAB SWITCHES never remount (GRO-2234): every VISITED tab keeps its editor mounted in its own layer, inactive layers hidden via `visibility: hidden` — never `display: none`, which would reset the scroller's scrollTop — so scroll position, caret, undo history and the unsaved buffer all survive a switch. Opening a DIFFERENT file in the same tab still remounts the Crepe host (`key={path}`): the old file's editor unmounts (→ autosave flush) and the previous file stays on screen until the next one has loaded.
5. **Outline folding** (GRO-2011): `createOutlineFolding()` (`src/editor/outline/`) is registered in `createCrepe()`. Parent `list_item`s (those owning a nested `bullet_list`/`ordered_list`) get a widget `<button class="outline-toggle" aria-expanded>` at the start of their content (one stroked SVG chevron sized by `--fold-chevron-size`, default 14px, rotated −90° via CSS when collapsed — GRO-2093; the 18px box is unchanged so strip/gate geometry holds); collapsing adds `data-outline-folded="true"` to EVERY nested list of the item (CSS `display:none`) — mixed markers at one indent (`* a` then `- b`) are unified on load (rule 8, GRO-2112); should sibling lists still arise (e.g. bullet + ordered), all of them fold (GRO-2031). Toggles are metadata-only transactions (`tr.docChanged === false`) — the listener never fires `markdownUpdated`, `getMarkdownForSave()` is unchanged, and the file's mtime is untouched. Fold keys = FNV-1a hash of the item's first-block text + occurrence index (`outlineFoldKeys.ts`), persisted via `storage.getFolds/setFolds`. Fold transactions carry one of: a position (toggle), `fold-all` / `unfold-all`, `{ set, collapsed }` (GRO-2107 guide-line click: any expanded → collapse all, else expand all), `undo-fold`; the multi-item ones remember the previous collapsed set so ⌘Z reverts them as one step.
6. **Accepted lossy normalisation** (standard remark-stringify behaviour; content preserved, formatting normalised): `-`/`+` bullets → `*` (alternating `-` for adjacent sibling lists), tabs → 2-space indent, `1)` ↔ `1.` ordered markers swap/renumber, setext → ATX headings, two-space hard breaks → `\`, trailing whitespace stripped, `___` → `***`, indented code → fenced, tables re-padded, lazy blockquote continuation gets `> `, `_`/`*`/`[`/`=`/`&` escaped in text where ambiguous, bare URLs/emails → `<autolink>`, file always ends with a single `\n`. First save of an untouched file WILL rewrite the file in this normalised form.
7. **Outliner keymap** (GRO-2012, `src/editor/outline/listCommands.ts`, registered in `createCrepe()` with keymap priority 100): Tab = indent (no-op on a first sibling — never inserts spaces), Shift-Tab = outdent (level 1 → paragraph; following siblings nest under the lifted item), Enter at the end of a parent item = new FIRST child (after the subtree when the parent is folded), Enter on an empty item = outdent / leave the list, Backspace at the start of an item = join into the previous paragraph (empty parent: children take its place; non-empty parent: no-op). Multi-item selection + Tab/Shift-Tab moves all selected items.
8. **Empty list items** (`src/editor/listItemRoundTrip.ts`): an empty bullet/ordered item is written as a bare marker (`*` / `1.`), never `* <br />` — `<br />` opens a CommonMark HTML block that swallows the item's nested children on reload. Parsing gives an item whose nested list starts on a later line (`* ` + children, Obsidian's empty parent) an empty leading paragraph; `* 1) text` on one line stays a list-first item. Before parsing, `normalizeEmptyItems()` rewrites legacy `* <br />` lines to bare markers and an empty task `* [ ] ` / `* [x]` to `* [ ] <br />` (remark alone reads `[ ]` as text and would write `* \[ ]`); on save `stripEmptyTaskBreaks()` writes it back as `* [ ]` — `<br />` never reaches the disk. **Mixed markers** (GRO-2112): the same pass runs `unifySiblingMarkers()` — `-`, `*` and `+` are one bullet: bullets at one indent parse as ONE list (the first sibling's marker wins on load; a blank line starts a new list, as in Obsidian). CommonMark would otherwise start a new list on every marker change. Line rules live in the function's docblock. Disk is untouched by loading; the first save writes `*` throughout (rule 6) as before.

9. **Depth bullet glyphs** (GRO-2013, `src/editor/outline/bullets.css`): CSS only — Crepe's bullet svg is hidden and `.label.bullet::after` draws ● / ○ / ■ by nesting depth of `.milkdown-list-item-block` (repeating every three levels; ordered levels count), `--list-indent: 2.15em`, marker colour 78% of the text colour, all from Crepe theme tokens. Heading-first items (`* # Part 1`) offset the label row by the heading's margin and size it to the heading's line box (`--list-label-offset/height`, shared with the fold chevron). Markdown untouched.
10. **Typography** (GRO-2009, `src/app.css`): Obsidian defaults — system font stack, 16px / 1.5 body, heading scale 1.802 / 1.602 / 1.424 / 1.266 / 1.125 / 1em at weight 600 (h1 700), line-height 1.3 — set through Crepe's `--crepe-font-*` / `--crepe-base-font-size` custom properties on `.editor-instance .milkdown`.

11. **Underline** (GRO-2028, `src/editor/marks/underline.ts`): ProseMirror mark `underline` (`<u>` in the DOM). On disk it is obsidian-underline's inline HTML `<u>text</u>`: a `$remark` plugin wraps each mdast `html("<u>")` … `html("</u>")` pair (nearest match, any depth, inside any inline parent such as `**…**`) into an `underline` mdast node after parsing, and registers the remark-stringify handler that writes it back as `<u>` + children + `</u>` — so `a <u>b</u> c` round-trips byte-identically. Unmatched tags and every other inline HTML keep going through Milkdown's `html` atom node unchanged. Not a Crepe feature (allowlist untouched, no toolbar button).

12. **Zoom into a bullet** (GRO-2029, `src/editor/outline/zoom.ts` + `zoom.css`): view state ONLY, like folding — the plugin holds the zoomed `list_item` position (mapped through every transaction; cleared if the item is deleted), and decorations hide every block off the path root → zoomed item (`outline-zoom-hidden`), strip the ancestors' glyph/chevron/first block (`outline-zoom-ancestor`, a folded ancestor renders expanded without touching fold state) and render a breadcrumb widget (`File name › Ancestor › … › Item`, labels = first-block text truncated at 40 chars; crumbs zoom to that ancestor, the file crumb zooms out fully). Triggers: click the bullet glyph (`.label-wrapper`; task checkboxes keep toggling), `Mod-.`, `Mod-Shift-.` (see Keyboard). Zooming dispatches a metadata-only transaction: never `markdownUpdated`, disk untouched, fold state unaffected. Not persisted — switching files remounts the editor and clears it, and an external file change (watcher → `replaceAll`) replaces the doc and clears it too. `createCrepe({ zoom: { fileName } })`; allowlist untouched. **History** (GRO-2091): every zoom change (glyph, crumb, `Mod-.`, `Mod-Shift-.`, zoom-out included) pushes one in-memory entry `history.state = { mdappZoom: { file, key } }` with the URL untouched (2-arg `pushState`; `key` = fold-key scheme over ALL list items, `null` = zoomed out), and `popstate` restores that level without pushing — so Back / Forward walk zoom levels. Entries of another file are ignored (left behind by a file switch → a Back press can be silent), an unresolvable key zooms out, the original page entry (no zoom state) = zoomed out.

13. **List guide lines** (GRO-2030, `src/editor/outline/guideLines.ts` + `.css`): every nested list (`li.list-item > .children > .content-dom > ul/ol`) gets a CSS `::before` strip — 10px wide, absolutely positioned (`-1 * (--list-indent / 2 + 10px)`) so its centred 1px line runs under the parent's glyph centre; zero layout shift, folded lists take their line with them, colours from `currentColor` (14%, hover 35%). Pseudo boxes hit-test as the list element, so a pointer left of the list's border box = the strip: the plugin's `handleDOMEvents` turns mousedown into `toggleOutlineFoldChildren(listPos)` (GRO-2107: folds / unfolds every parent item directly inside that list — the bullets alongside the line, never the line's owner; an all-leaf line is a swallowed no-op; mixed-marker siblings (GRO-2031) render as two lists with two lines and each line acts on its own list — markdown/mtime untouched, caret unmoved) and mousemove into the `outline-guide-hover` highlight (element `:hover` would light up while editing text inside).

25. **Backlinks — "Linked mentions"** (Links D, GRO-2193, `src/links/backlinks.ts` + `BacklinksSection.tsx` + `backlinks.css`; decision D of GRO-2096 and the GRO-2193 placement thread, both LOCKED). **Storage**: none — the referencing set is computed CLIENT-SIDE in ONE pass over the index snapshot the window already holds (`backlinksFor`), through THE shared resolver (`resolverFor`, see "Link resolution"). A mention is a record's `links` **or** `embeds` entry resolving to the open path — an `![[embed]]` mentions its target exactly like a `[[link]]` — with the open note itself excluded, ONE entry per referencing note however many mentions it holds, path-sorted. Code is skipped through the rename engine's length-preserving `maskCode` (the index's `stripCode` mirror), and frontmatter lines scan like any other — the index reads links there too, though only as whole-value exact `[[…]]` strings, so a frontmatter line CAN highlight a mention the index did not count (GRO-2197 audit, deferred). A skeleton bar shows while a read is in flight; a FAILED read leaves the entry standing WITHOUT snippets — never a dialog, never a notice. **Live**: a fresh snapshot recomputes N (and drops the whole section when the last mention goes); an EXPANDED entry re-reads its snippets only when its own record's `mtime` moved — changed files only, so unrelated vault activity costs no reads. **Clicks**: plain → the CURRENT tab (`openCurrent`), ⌘ → a BACKGROUND tab (`openBackground`) — the same model as wiki-link clicks (rule 23) and sidebar rows; entry title and snippet rows behave identically (title = basename, tooltip = the full path). **Collapse state** is per-component and in-memory: since every visited tab keeps its editor layer mounted (rule 4) it is effectively per tab for the session, and it is never persisted — an open backlinks block is not part of a note's identity. **Feed**: the per-window `WikilinkResolveSource` carries the resolver AND the snapshot it was built from (`update(resolve, records)`, fed by `WikilinkIndexBridge` — one snapshot feed for decorations, the picker and backlinks alike), so N can never disagree with the resolution behind it; the section subscribes to the source directly, so index updates never re-render App or remount an editor.

## Bases modules

### Property index (GRO-2127 contract, GRO-2128 index — now in the Electron main process)

The query engine behind `.base` views reads notes through `IndexRecord`, never the filesystem. Transport: bridge method `index(root)` (Desktop D10), no HTTP anywhere — the index (`desktop/src/main/vaultIndex/`) is transport-agnostic (tests call `getIndex` directly); it moved, not rewrote, from the retired server process (GRO-2157).

Files: `shared/types.ts` (`IndexRecord`, `IndexResponse`), `shared/frontmatter.ts` (`splitFrontmatter` — moved from the client, which re-exports it — and `parseFrontmatter`), `desktop/src/main/vaultIndex/scan.ts` (`scanFile` + pure `extractAliases` / `extractTags` / `extractLinks` / `extractEmbeds`), `desktop/src/main/vaultIndex/registry.ts` (`getIndex`, cache + watcher), `desktop/src/main/vaultIndex/index.ts` (barrel), `client/src/bases/testRecords.ts` (`TEST_RECORDS`).

`IndexResponse { root, records: IndexRecord[], generatedAt }` — `records` is every `.md`/`.markdown` file under `root` (dot-entries and `node_modules` skipped, exactly like `tree(root)`), sorted by path. `.base` files, images and everything else are never records.

| `IndexRecord` field | Value |
|---|---|
| `path` | absolute |
| `name` / `basename` / `ext` | `VSL-v1.md` / `VSL-v1` / `md` (`md` or `markdown`, lower-case, no dot) |
| `folder` | root-relative, `/` separators, `''` at the root (`Content Pillars/1. Agentic Agency`) |
| `size` / `mtime` / `ctime` | bytes / mtime ms / birthtime ms (ctime ms where the platform has no birthtime) |
| `properties` | frontmatter parsed with yaml's default **core** schema: `null`/booleans/numbers typed, dates stay strings (`date: 2026-08-01` → `'2026-08-01'`), `pillar: null` is present with value `null`. `{}` when there is no frontmatter, the block is not a map, or YAML fails — the latter two also set `frontmatterError` (one-line yaml message or `frontmatter is not a map`). Files over `MAX_FILE_BYTES` are stat-only (`{}`, empty lists, no error). |
| `aliases` | frontmatter `aliases` — extra NAMES the note answers to (Links E2, GRO-2214): a list → each string item; a scalar string → ONE alias (never comma-split, the deliberate contrast with `tags`); trimmed, empties and non-strings dropped, de-duplicated (first appearance). Absent / non-string → `[]`. Only the `aliases` key (Obsidian's), never `alias`; nothing is stripped from a value, so `aliases: ["[[X]]"]` is an alias literally named `[[X]]`. |
| `tags` | frontmatter `tags`/`tag` (list → each string item; string → split on commas/whitespace; non-strings ignored; leading `#` stripped) followed by inline `#tags` in order of appearance. Inline rule: `#` preceded by start of text, whitespace or one of `( [ , ;`, then `[A-Za-z0-9_/-]+` with at least one non-digit (`#123` is not a tag), case preserved, nested `a/b` kept whole. Never inside fenced code (``` or ~~~), inline code spans or `http(s)://…` runs. De-duplicated, first appearance wins. |
| `links` | `[[target]]` targets with `\|alias`, `#heading` and `#^block` stripped and trimmed — frontmatter string values (top-level and inside lists) that are exactly `[[…]]` first, then the body. Embeds are excluded, and so is everything under the `aliases` key whatever it looks like (GRO-2214: an alias is one of this note's own NAMES, never an outgoing link). De-duplicated. |
| `embeds` | `![[target]]` targets from the body, same stripping, de-duplicated. |

Tags, links and embeds share one code-stripping pre-pass (`stripCode` in `scan.ts`): nothing inside a fenced code block (``` or ~~~) or an inline code span counts, matching Obsidian's metadata cache; `http(s)://…` runs are additionally ignored for tags only. Frontmatter values are never code-stripped.

`TEST_RECORDS` (`client/src/bases/testRecords.ts`) is the 8-note `bases-fixture` as records rooted at `/vault` with `size`/`ctime`/`mtime` zeroed; `desktop/src/main/vaultIndex/registry.test.ts` deep-equals the live scan to it, so client query tests and the main-process index are pinned to one truth.

Cache lifecycle (`getIndex(root)`):
1. First call: walk the root (`isSkipped` pruning, markdown only, 32 reads in flight), `scanFile` each file, keep a `Map<path, IndexRecord>`; concurrent first calls for one root share the single scan. A missing / non-directory root rejects with the same `BridgeFailure` codes as the fs bridge (`NOT_FOUND`, `NOT_A_DIRECTORY`, `FORBIDDEN`).
2. The root's shared chokidar watcher (`watchers.subscribe`) keeps the map live: `add`/`change` on a markdown path → re-`scanFile` and replace (a file that vanishes before the scan is dropped), `unlink` → delete, `unlinkDir` → delete every record under it; `addDir`/`ready`/`error` are no-ops. No rescan is ever needed.
3. Every call returns the map sorted by path with a fresh `generatedAt` and resets a 10-minute idle timer; on expiry the watcher subscription is released and the map dropped (the next call rescans). Test hooks: `_evictAll()`, `_setIdleMs(ms?)`.

Persistent cache (GRO-2223, decisions D1–D4 — write GRO-2228, load GRO-2229): the record map additionally persists as one JSON per vault in `app.getPath('userData')/index-cache/<first 16 hex of sha256(root)>.json` (`desktop/src/main/vaultIndex/cache.ts` — Electron-free like `store.ts`: `main/index.ts` injects the dir via `initIndexCache`; the vault itself is never written, and cross-machine sync of the cache is a non-goal — the reconcile makes a foreign cache harmless anyway). Payload `{ version: CACHE_VERSION, root, records: IndexRecord[] }` (the constant is **2** today — see the load rules below); records whose frontmatter cannot round-trip through JSON (non-finite numbers — YAML `.inf`/`.nan` — or self-referential alias cycles) are left out of the write and simply rescan on the next start; the rest of the vault still caches. Persists are debounced ~5 s per root (`schedulePersist` — called from the watcher-incremental mutations, build success, and idle eviction as a natural last flush point) and land through the same `atomicWrite` as everything else, chained per root so writes never reorder; `flushIndexCache()` writes every pending root at once and joins `store.flush()` in the `before-quit` chain. `.obsidian/types.json` never enters the payload: `getIndex` reads it fresh per call, so a types change shows on the very next response even under a full warm hit — there is nothing to invalidate. GC (GRO-2230): `initIndexCache` sweeps the dir once per launch — ANY file (cache JSONs and crashed `.tmp-` leftovers alike) whose mtime is older than 90 days (`GC_MAX_AGE_MS`) is deleted, so vaults never reopened stop accumulating dead files. Every vault open refreshes its file's mtime (build success schedules a persist), so only truly abandoned entries age out, and a wrongly deleted cache is self-healing — exactly one full rescan. Deliberately minimal: no size caps, no LRU, no registry.

THE INVARIANT: the cache is only an accelerator — a wrong, missing, stale or corrupt cache can never produce wrong data. `loadIndexCache(root)` never throws; it answers `{ records, status }` with status `hit`, or degrades: `miss` (no file, or the payload names another root — a hash-prefix collision or a copied cache dir is simply not this vault's cache), `corrupt` (unparsable JSON, wrong shape, or any structurally malformed record — one bad element poisons the whole file), `version-mismatch` (numeric `version` ≠ `CACHE_VERSION`, now **2** — E2 added `aliases` to the record shape, GRO-2214). On build, `reconcile(root, files, load)` (`reconcile.ts`) turns the load into the live map: a non-hit is exactly today's full `scanAll`; on a hit it stat-sweeps every walked-and-cached file and reuses a cached record only when path + mtime + size all match (D2 — the record is its own validation key), `scanFile`-ing anything new or differing and dropping per-file stat/scan errors silently (same semantics as `scanAll`). The sweep is a sync `statSync` loop (~27 ms at 10k notes) and the cache load happens before `subscribe`, because the fresh watcher's initial scan floods the 4-thread libuv pool right at build time — async stats queue FIFO behind it and drain at the watcher's pace (~10× slower measured); warm 10k start lands ~99 ms vs ~1040 ms cold (GRO-2229 bench). A corrupt cache file is ignored IN PLACE (one `console.warn` at build) and overwritten by the next persist — deliberately unlike `store.ts`, which moves corrupt user state aside as `.corrupt-<epoch>` for forensics: the cache is derived data whose source of truth is the vault itself, so a corrupt copy holds nothing worth keeping, and move-aside would only accumulate junk for the GC to learn about (GRO-2230). RULE: any change to `IndexRecord`'s shape or the scanner's extraction semantics MUST bump `CACHE_VERSION` (`cache.ts`) — an old snapshot must never be read as if it had the new semantics; discard IS the migration (a mismatch degrades to one full rescan, there is no converter), and the fingerprint pin in `cache.test.ts` fails on such a change until the bump lands.

The reconcile also emits the cold-start diff for E1c rename detection (GRO-2242): `getColdStartDiff(root)` → `ColdStartDiff { root, scannedAt, cacheStatus, added, removed, changed }` (= the shared `ColdStartDiffResponse`, shipped to the renderer verbatim as the bridge's `coldDiff(root)`), held on the live entry and dropped with it on idle eviction. `added` carries ON-DISK stats and `removed` the CACHED stats — their (size, mtime) join is the rename signal; `changed` lists paths whose mtime or size moved. Miss semantics are honest: on any `cacheStatus` other than `hit` there is no before-snapshot, so all three lists are EMPTY (never "everything added") and `cacheStatus` says why — consumers must check `cacheStatus === 'hit'` before trusting them. Test hooks: `_resetIndexCache()`, `_setPersistDebounceMs(ms?)`, `_gcDone()`.

### Engine (GRO-2132 function library, GRO-2133 filters / sort / group / limit, GRO-2134 summaries)

`client/src/bases/engine.ts` — `runView(def, view, records, { thisFile?, root? }) → ViewResult { rows, groups, summaries, errors, total }`, pure and DOM-free, never throws. Pipeline: filters → values → sort → limit → group → summaries. A record passes when the base-level `def.filters` AND the view's `filters` both pass; `and` / `or` / `not` nest (`not` = none of the children true); a leaf is truthy per `isTruthy` (an ErrorValue fails). Every filter string is compiled once (`compile()` cache); a compile error or a malformed node makes that whole filter reject every row and adds one `EngineError { where, message }` — `where` is `filters` / `views[i].filters`, with `[j]` per child (`views[0].filters[1][0]`). `Row { record, file: FileValue, values }` — `values` is keyed exactly as the view writes the key (`view.order`, else `propertyKeys`): `file.x` is the file field, `formula.x` evaluates the formula (a compile error → ErrorValue cell + one `EngineError` at `formula.x`; an unknown formula is the evaluator's `unknown formula x` ErrorValue with no report), anything else is the note property (`note.` prefix optional) through `fromYaml`. Sort: `view.sort` in priority order, type-aware (numbers, dates/durations by ms, strings `localeCompare` base-insensitive + numeric, booleans false < true, lists by first element, links by target, mixed types by rank), null / missing / ErrorValue always last whatever the direction, path as the final tiebreak. `limit` applies after sort and before grouping; `total` is the pre-limit count. `groupBy` → one `Group { key, label: render(key), rows, summaries, fannedOut }` per distinct key (`equals`), ordered by `groupBy.direction` with the same comparator; null / `''` / empty list / ErrorValue rows go to a trailing `{ key: null, label: 'No value' }` group that is always last; no `groupBy` → `groups: null`. **Fan-out** (YAZ-671 D1): a LIST value joins the entry to one group per DISTINCT non-empty element (`equals`, no resolver — so link identity is the exact target, and two spellings of one note stay two groups), never a combination group; empty elements drop and a list left with none falls to "No value" like `[]` already does. `Group.fannedOut` is true on EVERY group of such a grouping (the "No value" group included) and false otherwise — it is what the group-derived writes read. A fanned-out row is counted in each group it joins, so per-group summaries can sum ABOVE `total` while the footer stays de-duplicated over `kept` (D2, deliberate). `groupKeyOf` keys shift from the rendered list to the rendered element, so collapse state persisted against an old combination group simply never matches again — orphaned, harmless, no migration. `this` is the `FileValue` whose path equals `opts.thisFile`, else null. `propertyKeys(def, view, records)` is `view.order` if set, else `file.name` + every note key seen (sorted, as `note.<key>`); `propertyLabel(def, key)` is `def.properties[key].displayName` (looked up as written, bare and `note.`-prefixed) else the key without `note.`. Budget: 1000 records × 3-clause filter + 2 formulas + sort + groupBy under 50 ms (`engine.test.ts`).

Link resolution (`makeResolver(files, root?, opts?)`, also `Scope.resolve`): a target matches by absolute path, then root-relative path (with or without `.md` / a leading slash), then bare basename — duplicate basenames resolve to the SHALLOWEST folder (Obsidian's shortest-path rule, GRO-2190), equal depth to the first in path order — and finally, LAST, a frontmatter ALIAS (Links E2, GRO-2214): a real name always beats an alias, whatever their depths, and two notes claiming one alias follow the same shallowest-then-first-in-path-order rule. An alias is a bare NAME, so it never joins a folder path (`[[Costs/CAC]]` does not resolve through the alias `CAC`). Case-insensitive throughout, `[[…]]` / `|alias` / `#heading` stripped. `opts.aliases: false` builds a NAME-ONLY resolver — the rename engine's referencing-set probe (see "Links": Rename), the one consumer that must NOT see aliases. `resolverFor(records, root?, opts?)` is the memoized accessor (WeakMap keyed on the records array identity, then per root and alias mode): everything reading the SAME snapshot gets ONE resolver — a refetched index is a new array and gets a fresh one; the per-resolver target cache is unchanged. Precisely (GRO-2197 audit — the earlier wording overclaimed): the resolver is one IMPLEMENTATION everywhere and the wikilink surfaces genuinely do share one INSTANCE, because `WikilinkIndexBridge` is the window's single index feed for decorations, the picker and backlinks alike (rules 23/24/25). `runView` does not share it: `BaseHost`, `BaseEmbed` and `BaseCodeBlock` each run their own `useIndex`, so each holds its own snapshot array and therefore its own memo entry. Semantics are identical — only the instances and the fetches are duplicated (recorded, not fixed). It backs the global `file(path)`, `link.asFile()`, and tightens `file.hasLink()`, `link.linksTo()` and link `==` to compare resolved paths — an unresolved side (e.g. `levels.png`, not a note) falls back to the textual `linkTargetsMatch`. Without a resolver `file()` / `asFile()` stay ErrorValues and matching is textual. List helpers `sum() mean() median() min() max()` ignore non-numbers and give null on none.

`client/src/bases/summaries.ts` — `summarize(kind, values, custom?)`: built-ins (`BUILTIN_SUMMARIES`, case-insensitive) `Count` / `Empty` / `Filled` / `Unique` on any type (`isEmpty`, `equals`), `Average` / `Max` / `Median` / `Min` / `Range` / `Stddev` (population) / `Sum` on numbers (non-numbers ignored, none → null), `Earliest` / `Latest` / `Range` (→ duration) on dates, `Checked` / `Unchecked` on booleans; a non-built-in kind is looked up in `custom` (= `def.summaries`) and evaluated with `values` bound to the column (`Scope.extra`), else `ErrorValue('unknown summary kind: …')`. `runView` fills `result.summaries[prop]` over the post-limit rows and `group.summaries[prop]` per group from `view.summaries { prop: kind }`.

### View chrome (GRO-2135)

### Cell editing (5B — GRO-2141 write path, GRO-2142 editors)

`writeProperty(path, key, value)` (`client/src/bases/writeProperty.ts`) changes ONE frontmatter key of a note on disk: read the current bytes, `setFrontmatterProperty` (`shared/frontmatter.ts`) rewrites just that key, write with `expectedMtime`; on `CONFLICT` it re-reads once and retries — the value the user picked wins over a concurrent edit elsewhere in the file, which is preserved because only this key is rewritten; a second conflict throws (two racing writers means something else is fighting us). Broken frontmatter (`FrontmatterWriteError`) propagates and nothing is written; a no-op edit never touches disk (same rule as the editor's autosave).

Editor inference (`client/src/bases/editorType.ts`, locked precedence): an explicit `.obsidian/types.json` assignment (delivered as `IndexResponse.types`) wins over any inference from values; otherwise the note's own YAML value decides; a note without the key borrows the dominant value type across the view's records; text is the final fallback. `file.*` and `formula.*` never get an editor (read-only). Kinds: text / number / checkbox / date / list / link.

`view/EditableCell.tsx` is one editable property cell, shared by table cells and card/list property rows: the display (typed like a read-only cell) opens the editor on click — or on Enter, via the host view clicking `[data-edit]` — Enter/blur commit through `writeProperty`, Esc cancels; the link editor completes `[[…]]` over the index's basenames through the shared matcher (`links/completion.ts` — one matcher with the editor's `[[` picker, rule 24; GRO-2191). Commits are optimistic: the committed value renders immediately and stays until the index refetch delivers it; a failed write reverts the cell and shows an inline error. Checkboxes are live and commit on every toggle, no edit mode. An untouched chips editor (no chip added/removed, no pending text) never commits — its seed stringifies the list, so a no-op commit would rewrite `[1, 2]` as `['1', '2']` (7B, GRO-2148). The note's own open editor window absorbs the resulting frontmatter-only `change` silently (GRO-2186, see the autosave note under "Bridge API").

### Group drag (5C — GRO-2143)

`view/groupDrag.ts`, shared by the board's columns and the grouped table's sections. `dragKey(view)` is the bare frontmatter key a drop writes — null (drag disabled) unless `groupBy` is a note property; drag is also off in read-only embeds. `useGroupDrag(key, onMove)` owns the transient HTML5 drag state: `source(path, gk)` spreads on each card/row, `target(group)` on each column/section (rows included — events bubble), the hovered target highlights, a drop on the source group is a no-op, and Esc cancels (real drags fire `dragend`; a document keydown fallback covers jsdom). A drop on ANOTHER group fires `onMove(path, value)` with the target's raw YAML value read off that group's FIRST row — so the written type matches what the members already carry — or `undefined` for "No value", which DELETES the key. **Fanned-out groups SWAP instead** (YAZ-671 D3): because the row sits in several groups, overwriting with a neighbour's whole list would destroy its other values, so `onMove` carries a third `GroupSwap { remove, add }` argument — `remove` is the source group's value (`drag.key`, which is why the drag state carries the group VALUE and not just its `groupKeyOf` string) and `add` is the target's; either is null at "No value". BaseView edits the page's list rather than replacing it: elements are matched with the engine's own `equals` over `fromYaml` and NO resolver — the exact comparison that decided the grouping — so a swap can only remove the element that put the row in that group, and every other value survives. Dropping a fanned-out row on "No value" removes just that element and never deletes the key. `dragKey` is now `groupByKey` (one name; the group "+" needs the same key whether or not a drag is in flight). BaseView owns the optimistic side: `PendingMove { key, value, prevRaw }` per path, patched into the records BEFORE the engine runs (`applyMoves`) so the card lands in its target group with sort/values/summaries consistent, committed through 5B's `writeProperty`. Clearing follows 5B's discipline — an entry clears only when the index refetch moves that key's raw off `prevRaw` (our write landing, or a concurrent writer winning), never before. A failed write drops the move (the card snaps back) and flags the card/row inline (`moveError`). Tests: `view/GroupDrag.test.tsx`.

### New note (5D — GRO-2144)

`newNote.ts`, behind the toolbar's **New** button and each group header's "+" (both absent in read-only embeds). `deriveSeed(def, view)` is pure over the filter ASTs (def + view): equality leaves `note.x == <literal>` seed `x` with the literal's YAML type, `file.hasTag("t")` appends to a `tags` list, and a single `file.inFolder("…")` names the root-relative target folder — only **and-reachable** leaves count (`or`/`not` subtrees are skipped entirely; seeding those would not, or would anti-, satisfy the view), and non-equality rules are ignored by design (locked kickoff decision). A group "+" additionally seeds the group's property with the raw value of that group's first row ("No value" seeds nothing). Under FAN-OUT (YAZ-671 D4) it seeds `[render(group.key)]` instead — that group's own element as a one-item list, because the first row's raw value is a neighbour's WHOLE list there; `render()` returns a link to its `[[…]]` form, the same one the picker inserts. "No value" still seeds nothing. The note goes to `targetFolder`: the `inFolder` seed under the root, else the base file's folder, else the root; the name is `untitledName` over the basenames already in that folder (`Untitled`, `Untitled 2`, `Untitled 3`…). `createNewNote` creates the file over the bridge, then writes the seed frontmatter as ONE `writeFile` keyed to the created mtime (`seedContent` via `setFrontmatterProperty`; an empty seed writes nothing). Success opens the note; failure shows `.base-view__error` "Could not create note: …" and opens nothing. Tests: `newNote.test.ts`, `view/NewNote.test.tsx`.
